Why Did My Robot Fail?

Explainable fault detection and diagnosis for mobile robots · PhD project, Promotionskolleg NRW and Hochschule Bonn-Rhein-Sieg

When a robot misbehaves, a typical fault detector raises an alarm with an anomaly score. It tells you that something is wrong, but not which component is at fault or why, so the whole robot has to be inspected. This PhD research builds fault diagnosis that a person can read: each diagnosis names the faulty component, the rule of normal behaviour it broke, and the sensor evidence behind it.

Left: the output of a typical fault detector. Right: the output of the proposed approach for the same fault.

How It Works

  1. Segment and classify. Sensor signals are cut into segments, and each segment is described by its qualitative shape, for example constant, rising or falling.
  2. Learn the robot’s actions. Inductive Logic Programming (ILP), using the Popper system, learns short, readable rules for each robot action (driving straight, turning, driving a curve) from a few minutes of fault-free driving.
  3. Detect. When a rule is violated or a signal looks abnormal, the system raises an alarm and lists the components that could be responsible.
  4. Confirm. Residuals between redundant sensors (wheel odometry, IMU, laser scanner) are checked. A component is only diagnosed if this evidence supports it, which keeps false alarms low.
  5. Explain. The output names the faulty component together with the violated rule and the residual evidence.

The approach is evaluated on a TurtleBot3 mobile robot, with injected sensor faults and with physical faults such as an obstructed laser scanner and wheel faults. Ongoing work looks at learning the residuals themselves with ILP, transferring learned models to other robots, and turning diagnoses into natural-language explanations that are checked against the diagnosis trace.
